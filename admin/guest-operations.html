Design concept

A reliable check‑in appliance, not a tablet with a loose form

Target flow: match the reservation, collect the minimum justified guest data, verify identity where proportionate, record acceptance of rules/privacy information, confirm payment/access status, and create an auditable stay record. The counter tablet is the fallback/onsite interface; pre-arrival mobile check‑in should do most of the work.

Target guest journey

1. Pre-arrival: secure link sent against the reservation → guest confirms details and expected arrival.
2. Identity: ID sighted/verified where justified → verification result recorded; raw ID image not retained by default.
3. Consent & rules: privacy notice + house rules + any DVS express consent captured separately.
4. Arrival: guest uses mobile link or reception tablet → booking matched → staff exception path if anything fails.
5. Access: approved guest receives room/access instructions; future option for unique time-limited credentials.
6. Departure: checkout status recorded; access expires; any room inspection is a separate staff control.

Data & identity design

Best-practice direction is minimum necessary collection. A Victorian residents-register rule applies to accommodation providers with relevant general/on-premises liquor licences and requires name, address, room number and check-in/check-out dates; it says ID may be requested to verify details but a copy does not need to be kept. The property's actual licence status still needs to be checked.

DataProposed treatment
Booking reference, name, stay dates, room, contact detailsRetain for defined operational/recordkeeping purposes.
ID documentPrefer verify/sight → store result, type and transaction reference rather than the full image. Temporary scan may be used for OCR/verification if securely deleted.
DVS verificationPotentially viable as an approved private-sector business user through an approved Gateway Service Provider; requires approval, participation agreement and express consent.
Government Face Verification ServiceNot a launch dependency. Official guidance still describes private-sector FVS access as future/being rolled out; do not architect v1 around it.
Commercial selfie/liveness biometricsDefer unless a clear unattended-check-in need justifies it; conduct privacy impact assessment and avoid retaining reusable biometric templates.
Payment card dataUse external PCI-compliant processor; store transaction/status, not full card details/CVV.

Important: the current static GitHub “admin” area is not suitable for real guest records. Production guest data needs a separate authenticated application/database with MFA, role-based access, encryption, audit logging, backups, retention/deletion rules and a defined legal operating entity.

Wi‑Fi purchase at check‑in

Guest choice

Offer Wi‑Fi inside the check‑in flow

Once the booking is matched, the tablet already knows the guest, room and booked stay dates. It can offer an unlimited guest Wi‑Fi package before check‑in is completed: 1 night A$6, 2 nights A$10, 3 nights A$13, 7 days A$22, or 1 month A$55.

Automatic linkage

Payment → entitlement

Successful payment returns an event/reference to the backend. The system creates a Wi‑Fi entitlement linked to the guest ID, booking ID, room, paid package and validity period. The guest can receive a token/QR immediately and the captive portal recognises that reservation-linked entitlement.

Multi-device

One guest entitlement, several devices

The token is reusable for that customer's authorised devices rather than being consumed once. Each device that joins is enrolled against the same booking entitlement; a configurable device/concurrency ceiling can prevent sharing outside the room/booking.

Guest network only

Permanent building equipment bypasses this

TVs, CCTV, sensors, reception/check‑in hardware and other fixed building devices use permanent managed network credentials on separate operations/IoT networks. They do not see or pay through the captive portal.
