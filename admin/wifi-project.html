Architecture

Internet backhaul → router/firewall → managed access points → guest SSID / staff SSID / operations SSID
Guest SSID → captive portal → voucher/payment/approved guest access → internet
Operations network → check‑in tablet + staff devices + future locks/CCTV/sensors, isolated from guest traffic
Owner portal → remote monitoring, billing/audit records and device health — without exposing guest devices to admin systems

Why separate networks matter

Guest isolation

Guests should never share a trusted network segment with the check‑in database, reception equipment or future cameras/IoT.

Reliability

If guest traffic spikes, the reception/check‑in system still needs priority and predictable connectivity.

Security

VLAN/SSID separation, strong admin authentication and restricted management access reduce the blast radius of a compromised guest device.

Future value

Once reliable building connectivity exists, access control, environmental monitoring and maintenance telemetry become feasible.

What the captive portal is — and what it is not

Guest access only

A captive portal is the web page a guest is redirected to when they first join the guest Wi‑Fi network. Instead of giving every guest a permanent Wi‑Fi password, the portal checks their booking/entitlement and asks for a valid token before allowing internet access.

Not used by building equipment

Smart TVs, CCTV cameras, environmental sensors, the check‑in tablet, staff devices and other building equipment should be provisioned permanently on separate managed SSIDs/VLANs. They do not pay, see the captive portal or use guest tokens.

Multi-device entitlement

A paid entitlement belongs to the guest/booking, not to one device. The same token can enrol multiple guest devices. The backend records each authorised device against that guest and enforces a configurable device/concurrency limit.

Automatic expiry

Entitlements expire at the earlier of the purchased package end or the guest's recorded checkout, unless management deliberately extends them.

Preferred integration pattern

Square Terminal + Terminal API

Square's Terminal API can pair a Square Terminal with a custom application running on another device. The terminal handles contactless/NFC, chip/PIN and payment compliance; the backend receives checkout/payment events and can then issue the Wi‑Fi entitlement.

Square developer docs

Australian alternative

Tyro integrated EFTPOS

Tyro provides a browser-based JavaScript integration (iClient) for browser POS software to communicate with Tyro EFTPOS machines, plus Android/iOS options. This is attractive because the Fawkner check‑in UI is web-based.

Tyro integration docs

Tablet limitation

Lenovo tablet itself is not the card reader

The current Lenovo TB311XU/ZAEJ0157AU candidate is an LTE tablet but available specifications identify it as having no NFC. Therefore, direct Tap to Pay on that tablet should not be a dependency. Use an integrated EFTPOS terminal, or select a different certified NFC-capable device later.

Resilience

Payments need their own outage plan

The tablet's LTE backup protects the check‑in UI, but a separate payment terminal also needs connectivity. Network-level LTE failover or a cellular-capable smart reader is preferable if payment availability must survive a building WAN outage. Always retain a manual/online-link fallback.

Key risks

High

Single point of failure

Backhaul/router/AP failure can affect both revenue and operations. Keep operational fallback procedures and consider LTE backup at the operations layer.

High

Network segregation

Do not put guest traffic and the guest-management database on the same trusted LAN.

Medium

Support expectations

Charging for access creates an obligation to define refunds, support and what happens during outages.

Medium

Economics

Pricing, take-up and backhaul costs are still assumptions. The interactive calculator in the existing dashboard is scenario modelling, not a forecast.
